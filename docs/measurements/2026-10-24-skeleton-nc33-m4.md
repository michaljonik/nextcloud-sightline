# Walking skeleton on Nextcloud 33: previews, events, search

Date: 2026-10-24. Machine: MacBook Air M4 (dev, not the N305 target).

First end-to-end run of the planned architecture: the `sightline` app (`app/`) in a
Nextcloud 33 container, `sightline-embed` (`embed/`) on the host, LAION XLM-R B/32 as the
model. Questions: what does getting images out of `IPreview` cost, which events arrive for
trash, restore and moves, and does the Unified Search provider behave as planned?

## Setup

- `dev/compose.yaml`: `nextcloud:33-apache` (33.0.10, PHP 8.4.27, arm64 under OrbStack),
  Postgres 17. `sightline-embed` on the host, `nice -n 10`, 2 ONNX Runtime threads, reached
  from the container as `host.docker.internal`.
- Photos: 300 stock JPEGs from the model spike set, full size (7.1 MB on average, up to
  ~24 MP), uploaded over WebDAV. No HEIC or RAW in this run.
- `occ sightline:crawl` queues photos through `IFileAccess::getDistinctMounts()` and
  `getByAncestorInStorage()`; `occ sightline:index` drains the queue in the foreground and
  prints per-stage timings.
- Previews are requested at 1024×1024, `MODE_FILL`, with `cacheResult: false` (available
  since NC 32).

## Indexing cost

| Run | Photos | Preview p50 / p95 | Embed round trip p50 | Throughput | Preview storage growth |
|---|---|---|---|---|---|
| Cold, default `preview_max_x/y` 4096 | 198 | 894 / 1319 ms | 47 ms | 1.18 photos/s | +193 MB (~1.0 MB/photo) |
| Warm (max preview already exists) | 207 | 208 / 280 ms | 46 ms | 3.88 photos/s | 0 |
| Cold, `preview_max_x/y` 2048 | 100 | 554 / 858 ms | 47 ms | 1.56 photos/s | +33 MB (~0.33 MB/photo) |

- The embed round trip includes the image encode (43 ms p50) and HTTP. The 1024 px JPEG
  sent to the service averages 98 KB.
- **Preview generation dominates**: ~95% of per-photo time when no preview exists yet.
- `cacheResult: false` works as documented: only the max preview is stored (on average
  3684×2627, 992 KB), not the 1024 px one. The max preview is always generated and stored
  first; there is no way around it through `IPreview`.
- The warm case is what an instance that already shows thumbnails in Files, Photos or
  Memories pays: the max preview exists and only the downscale is left.
- Extrapolation to 200k photos, single worker, these M4 numbers: ~48 h and ~190 GB of max
  previews at the default 4096 px; ~31 h and ~65 GB at 2048 px. Not measured; the N305 will
  be slower per photo.

## Event order

Logged with `debug_events` on; folder-level cache events trimmed.

| Action | Events | File ID |
|---|---|---|
| Upload over WebDAV | `CacheEntryInserted`, several `CacheEntryUpdated`, `NodeCreated`, `NodeWritten` | new |
| Move to trash | `CacheEntryUpdated` with path `files_trashbin/files/<name>.d<ts>`, then `NodeDeleted` | kept |
| Restore from trash | `CacheEntryUpdated` (×3) with the original path, then `NodeRestored` | kept |
| Move to another storage (local external mount) | `CacheEntryRemoved` (old storage), `CacheEntryInserted` + `CacheEntryUpdated` (new storage), `NodeRenamed` | kept |
| File added outside Nextcloud, then `occ files:scan` | `CacheEntryInserted` only | new |

- Every change also emits `CacheEntryUpdated` for each parent folder up to the storage root
  (1385 events for 200 uploads). Cache events carry no mimetype, so the listener filters on
  the file extension.
- Trash is a move within the home storage. Because trash paths are skipped, only
  `NodeDeleted` signals it. Restore keeps the file ID, so the photo is encoded again (the max
  preview survived the trash, so this was the warm path: 236 ms).
- A cross-storage move keeps the file ID: the worker only updated `storage_id` on the service
  (`PATCH`), no re-encode.

## Search

- Unified Search shows a "Photos by content" category (order 50; Files is 5) with
  thumbnails from `core.Preview.getPreviewByFileId`; "Load more results" pages through the
  cursor; a result opens the photo in Files.
- End to end via `occ sightline:search`: 80–130 ms warm, 184 ms on the first query. Text
  encode 40–55 ms (2 threads, `nice`), vector scan ~1 ms at ~300 vectors.
- Polish and English queries return the same top results (e.g. "snowy mountains" /
  "ośnieżone góry").
- Permissions: a second user with only `Stock2` shared sees only `Stock2` photos, under
  their own path. The storage prefilter admits the owner's whole home storage (as expected),
  so the first page of 5 needed 16 candidates through `getFirstNodeById()`; still one round
  trip.

## Consequences for Sightline

- Preview generation, not the encoder, sets first-indexing time and disk use. Options to
  weigh on the N305: document `preview_max_x/y` 2048 (3× less storage, ~40% faster),
  Imaginary, or decoding JPEG/HEIC without `IPreview` for local storage. Measure HEIC and
  RAW previews before deciding.
- Use `cacheResult: false` (NC 32+, within the NC 33 minimum).
- Listen to both event families as planned; filter cache events by extension and storage
  path.
- Decide whether a trashed photo keeps its vector: keeping it avoids a re-encode on
  restore and is safe (trashed files fail `getFirstNodeById()` in the user folder), but then
  trash expiry must delete it (a `CacheEntryRemoved` under `files_trashbin/`).
