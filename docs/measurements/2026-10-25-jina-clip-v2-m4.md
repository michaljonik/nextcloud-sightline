# Jina CLIP v2 on a MacBook Air M4

Date: 2026-10-25. Machine: MacBook Air M4 (10 cores, 24 GB; dev, not the N305 target).
Adds one model to [the M4 model comparison](2026-10-24-model-comparison-m4.md): same 678
stock photos, same 27 judged English queries and their Polish translations, same
`spike.py` and `metrics.py`.

Question: jina-clip-v2 is often recommended for multilingual and long text queries. Does it
find better photos than LAION XLM-R B/32 (the default) or SigLIP 2 B/16, and what does it
cost?

## Model

| | |
|---|---|
| Export | `jinaai/jina-clip-v2`, `onnx/model.onnx` + `model.onnx_data`, fp32, revision `e10d47f5` |
| Licence | CC-BY-NC-4.0 (commercial use only through Jina's API or by contract) |
| Image tower | EVA02-L/14, 512 px input (short side resized, centre crop), 1.22 GB of weights |
| Text tower | Jina XLM-RoBERTa (the `jina-embeddings-v3` backbone), 2.24 GB of weights |
| Embedding | 1024 dims (Matryoshka; truncation was not tested) |

The repo ships one ONNX graph that takes `input_ids` and `pixel_values` together.
[`import_jina.py`](../../spikes/model-eval/import_jina.py) cuts it into an image and a text
graph so each side can be timed on its own; both parts give the same normalised vectors as
the full graph (max difference 4e-8). The graph has no attention-mask input, so queries are
not padded. No `trust_remote_code` was used.

The model card encodes queries with the prefix "Represent the query for retrieving
evidence documents: " (the `retrieval.query` prompt). Both variants were scored.

## Method

- As in the comparison: top 8 per query, nP@8 = relevant hits in the top 8 / min(8, number
  of relevant photos), MRR = 1 / rank of the first relevant photo.
- Jina's top 8 (both query variants, both languages) contained 103 photo-query pairs that
  no earlier method had returned. They were judged by eye the same way, with the photos
  already judged relevant for that query shown alongside. 11 were relevant (foggy morning,
  skiing, sad, crazy child ×4, snowy mountains, shallow depth-of-field ×3).
- The new relevant photos raise the denominator of a few queries, so some earlier models
  drop by up to 0.003 against the comparison note. All numbers below are from one run on
  the extended judgements.
- Timings: ONNX Runtime 1.31 CPU, batch 1, 60 photos at 1024 px, idle machine. XLM-R B/32
  and SigLIP 2 B/16 were re-timed in the same session (34 and 109 ms, matching the
  comparison note).
- One judge, stock photos, 27 queries: differences of a few points are indicative only.

## Cost

| Model | Image encode, 1 thread | Default threads (10) | Relative to XLM-R | Peak RSS, image side | Query, 1 thread |
|---|---|---|---|---|---|
| XLM-R B/32 | 34 ms | — | 1× | 0.5 GB | 43 ms |
| SigLIP 2 B/16-224 | 109 ms | — | 3.2× | 0.5 GB | 34 ms |
| **Jina CLIP v2** | **3,605 ms** | 2,379 ms (p90 3,831) | **106×** | 1.9 GB | 54 ms |

- The image side is what costs: a large ViT at 512 px (1,296 patches against 49 for B/32
  at 224 px). More threads help little: 10 threads are only 1.5× faster than one.
- Indexing the 678 photos took 31 minutes on the M4 with all cores.
- Query encoding is in the same range as the other models. Text-side RSS was 1.6–1.7 GB,
  but the weights are memory-mapped from the external data file, so this counts only the
  pages touched (most of the 250k-token embedding table is never read). It is not directly
  comparable to the other models, whose text towers are loaded whole.
- Extrapolated to the N305, using the N305/M4 ratio measured for XLM-R and SigLIP 2
  (6–7× on one thread, ~4× gain from 8 threads): about 22–25 s per photo on one thread,
  ~6 s on all cores, roughly two weeks of encoding for 200k photos. Not measured on the
  N305.

## Quality

| Model | nP@8 EN | nP@8 PL | MRR EN | MRR PL |
|---|---|---|---|---|
| XLM-R B/32 | 0.881 | **0.852** | 0.899 | **0.899** |
| SigLIP 2 B/16-224 | 0.836 | 0.819 | **0.946** | **0.899** |
| SigLIP 2 B/16-384 | **0.889** | **0.852** | 0.909 | 0.894 |
| SigLIP 2 L/16-256 | 0.885 | 0.762 | 0.944 | 0.829 |
| **Jina CLIP v2, no query prefix** | 0.869 | 0.790 | 0.902 | 0.842 |
| Jina CLIP v2, with `retrieval.query` prefix | 0.827 | 0.752 | 0.872 | 0.778 |

Queries better / worse than SigLIP 2 B/16-224 (nP@8): Jina without prefix 6 / 3 in English,
8 / 6 in Polish; with prefix 3 / 4 and 3 / 8.

- **The documented query prefix hurts here**: −4 points in both languages. It is the
  prompt Jina uses for text retrieval; for short photo queries the plain text works
  better.
- **English is on par with the B/32 and B/16 models**, not better: 0.869 against 0.881 for
  XLM-R B/32 and 0.889 for B/16-384.
- **Polish drops 8 points** (0.869 → 0.790), more than XLM-R (3) or SigLIP 2 B/16 (2). Most
  of the loss sits in three queries: "mglisty poranek" (0.25, XLM-R 0.62), "urządzenie
  zabezpieczające" (0.20, XLM-R 1.00) and "silnik odrzutowy" (0.50, XLM-R 1.00). Jina does
  better than XLM-R on "tata uczący dzieci", "grupowe zdjęcie uśmiechniętych ludzi" and
  "ulica miasta nocą".
- The model's strength is long multilingual text. Sightline's queries are a few words, so
  that strength does not show here.

## Consequences for Sightline

- **Not a candidate.** Below XLM-R B/32 in both languages at ~106× the image cost, and
  CC-BY-NC rules it out as a default of an open-source project in any case.
- Not tested: the int8 and fp16 exports, which would cut the cost by a small factor but
  not by the two orders of magnitude that separate it from XLM-R B/32.
- No change to the default (XLM-R B/32) or to the English-only option (SigLIP 2 B/16).
