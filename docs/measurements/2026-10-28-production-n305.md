# Production library on the N305: RAW files and search latency

Date: 2026-10-28. Machine: Intel N305 home server, Nextcloud 35.0.2 (official Docker image),
Imaginary for JPEG/PNG/HEIC, Camera RAW Previews (`camerarawpreviews`) 1.1.4,
`preview_max_x/y` 1024. Model: XLM-R B/32 (512 dims). `sightline-embed` limited to 4 CPUs and
3 GiB, `SIGHTLINE_THREADS=4`. All checks were read-only: SQL in read-only transactions, no
restarts, no writes.

At the time of the check the index held 122,972 photos, with 119,908 more queued.

## RAW files

Indexed and failed RAW files, joined from `oc_sightline_files` to the file cache by file ID:

| Extension | Indexed | Failed |
|---|---|---|
| DNG | 22,236 | 1 |
| NEF | 16,351 | 7 |
| ARW | 1,308 | 11 |
| NEF, macOS resource forks (`._*`, `.AppleDouble/`) | 0 | 2,563 |

The library has no CR2, CR3, ORF, RW2 or RAF files. Of the 19 failures that are real RAW
files:

- 6 are files of 0 bytes and one is a 165 KB NEF, probably truncated;
- 11 ARW files fail with "Unable to open preview stream" because an old preview record
  points at a preview file that no longer exists. The same error hits 1,776 non-RAW files,
  so it is not RAW-specific;
- one 30 MB NEF is the only failure that looks like a Camera RAW Previews miss.

The 2,563 resource-fork files are 0-byte copies that macOS writes to SMB volumes. Sightline
now skips them.

**Orientation.** The EXIF Orientation of each original (as read by Memories, `oc_memories`)
was compared with the shape of its stored 1024 px preview, which is the image Sightline
receives:

| Extension | Orientation 6 or 8 | Portrait preview |
|---|---|---|
| NEF | 2,191 | 2,191 |
| DNG | 2,883 | 2,883 |
| ARW | 250 | 250 |

None stayed landscape. The preview JPEGs have no orientation tag, so the rotation is in the
pixels: Camera RAW Previews 1.1.4 applies the RAW file's orientation itself. Six portrait
previews checked by eye (three tagged 8, three tagged 6) were upright; one close-up was
ambiguous but probably upright. Older versions of the app were not checked.

## Search latency

`POST /search` from the Nextcloud container, 20 queries (10 English, 10 Polish) × 3 runs per
scenario, 50 results per page, after two warm-up requests. No indexing ran during the
measurement. Times in ms, p50 / p95:

| Scenario | Text encoding | Scan | Wall clock |
|---|---|---|---|
| All 7 storages (122,972 vectors), first page | 94 / 115 | 126 / 129 | 223 / 245 |
| One storage with 152 vectors | 94 / 96 | 60 / 62 | 157 / 161 |
| All storages, results 201–250 | 93 / 96 | 159 / 164 | 255 / 259 |

- Encoding the query costs about 93 ms on 4 threads, every time; there is no cache.
- The storage filter does not shorten the scan much: a storage with 152 vectors still takes
  60 ms, because sqlite-vec reads the whole table. The scan grows with the number of
  results requested (126 ms for 50, 159 ms for 250).
- HTTP and JSON add 3–5 ms.

End to end, `occ sightline:search` for 5 queries as a user with 8 mounted storages: 357–367 ms
for 50 results and 279–290 ms for 10, of which about 210 ms is the service. Nextcloud's
share (mount cache, the HTTP call, one `getFirstNodeById()` per result) is about 1.5 ms per
result. Search while indexing runs was not measured.

Memory of `sightline-embed`: 759 MB before and 765 MB after the run. The peak since the
container started was 2.58 GB. The vector database is 246 MiB for 122,972 vectors; the model
files take 1.4 GiB.

## Indexing runs only at night

`IndexJob` is time-insensitive, and this instance sets `maintenance_window_start`, so
Nextcloud runs the job only in its maintenance window, which starts at 01:00 UTC here. Rows
were indexed only between 01:00 and 05:59 UTC, about 4,600 a night. At that rate the 119,908
queued files need about 25 more nights. Running `occ sightline:index` indexes in the foreground at any time
(7,728 photos in 70 minutes on the same machine, earlier).

Since this check `IndexJob` is time-sensitive and runs around the clock.
